# Smile ID for Expo KYC and returning-user authentication

**Research date / primary-source access date: 2026-10-26.** Scope: current v12 mobile SDK and v3 API documentation, official SDK package metadata, and official Smile ID web pages. No application code was changed.

## Verdict

**Yes, with two important limits.** An Expo app can run Biometric KYC once, reuse the resulting Smile ID enrollee for later SmartSelfie Authentication, and separately retain the enrollment selfie to compute a private 1:1 embedding. A second SmartSelfie Enrollment job is not required after Biometric KYC. The official Web SDK documentation explicitly says Authentication can use a user enrolled earlier “by SmartSelfie, Biometric KYC, or one of the mobile SDKs.” [Smile ID — Performing a Verification, SmartSelfie](https://docs.usesmileid.com/developer-resources/sdks/web/web-sdk/performing-a-verification)

However, the documented SmartSelfie Authentication job bundles vendor liveness **and vendor face matching**; there is no documented liveness-only switch whose result can be combined with only our own matcher. A private local/server-side 1:1 match is feasible as a separate decision path, but then Smile ID's capture-time face detection must not be mistaken for vendor liveness. [Smile ID — Authenticate a User's Biometrics](https://docs.usesmileid.com/api-reference/products/smartselfie-authentication/authenticate-a-users-biometrics), [Smile ID — mobile capture configuration](https://docs.usesmileid.com/developer-resources/sdks/mobile/performing-a-verification)

## Expo / React Native integration

- Use the current **v12** packages: `@smileid/usesmileid` plus the face analyzer providers (`@smileid/usesmileid_mlkit_face` on Android and `@smileid/usesmileid_vision_face` on iOS); document providers are unnecessary for selfie-only Biometric KYC and SmartSelfie. The published `latest` package version observed through npm metadata was **12.3.0**, matching the current setup documentation. [Smile ID — mobile overview](https://docs.usesmileid.com/developer-resources/sdks/mobile), [Smile ID — Setup](https://docs.usesmileid.com/developer-resources/sdks/mobile/setup), [npm — @smileid/usesmileid](https://www.npmjs.com/package/@smileid/usesmileid)
- Current floors are Node **20.19+**, React **19.2+**, React Native **0.83+** or Expo SDK **56+**, Xcode **16+**, Android `compileSdk` **36+** and `minSdk` **24**. Expo SDK 56 implies an iOS **16.4** target. From 12.1.0 the SDK is built/verified against Expo 57 / RN 0.86 while retaining those floors. [Smile ID — Setup, prerequisites](https://docs.usesmileid.com/developer-resources/sdks/mobile/setup)
- The SDK requires React Native's **New Architecture**, native config plugins/prebuild, camera permission declarations, explicitly registered ML providers, and a backend-minted short-lived v3 token. A long-lived API key must not ship in the app. [Smile ID — Setup](https://docs.usesmileid.com/developer-resources/sdks/mobile/setup)
- **Expo Go is not supported.** Use an Expo development build via `npx expo run:ios` / `npx expo run:android`, EAS Build, or a release build containing the native modules. [Smile ID — Setup, Step 1](https://docs.usesmileid.com/developer-resources/sdks/mobile/setup)
- The v12 API is `UseSmileIDBuilder`: compose consent, selfie `capture`, optional instructions/preview, and `processing`; select `JobType.biometricKyc` or `JobType.smartSelfieAuthentication`. Biometric KYC additionally needs `biometricKYCParams` (`idType`, `idNumber`, `country`) and `userDetails`; no document capture is involved. [Smile ID — Performing a Verification](https://docs.usesmileid.com/developer-resources/sdks/mobile/performing-a-verification)

## Capture and backend REST options

- Normal SDK submission captures the selfie/liveness frames and submits directly to Smile ID. Setting `config.skipApiSubmission = true` instead returns a `captured` result containing `selfieImage`, ordered `livenessImages`, headers, and the sealed `encryptedPackage` / nonce / tag. Our backend can forward that package unchanged to Smile ID; the app must delete retained capture files after handoff. This is the cleanest official route to retain one enrollment selfie privately before backend submission. [Smile ID — Getting Result, Submitting from your own backend](https://docs.usesmileid.com/developer-resources/sdks/mobile/getting-result-of-a-verification)
- Direct backend REST submission is also documented: Biometric KYC accepts multipart `selfie_image` plus 6–8 `liveness_images`, `country`, `id_type`, and `id_number`; Authentication accepts multipart `user_id`, `selfie_image`, and 6–8 `liveness_images`. Thus the SDK is not mandatory as the submitter, although capture still has to produce acceptable images and liveness frames. [Smile ID — Biometric KYC API](https://docs.usesmileid.com/api-reference/products/biometric-kyc/perform-a-biometric-kyc-verification), [Smile ID — Authentication API](https://docs.usesmileid.com/api-reference/products/smartselfie-authentication/authenticate-a-users-biometrics)
- If using normal SDK submission instead, the Biometric KYC webhook exposes `image_links.selfie_image` as a signed URL that expires after **15 minutes**. A backend intending private retention must copy it promptly rather than store that URL as the durable reference. [Smile ID — Biometric KYC webhook](https://docs.usesmileid.com/developer-resources/essentials/verification-webhooks/webhook-types/biometric-kyc)

## Enrollment identity, parameters, and results

- **Biometric KYC enrollment is reusable for Authentication; do not run a separate enrollment by default.** Persist the returned Smile ID `userId` server-side against our account and supply that same value as `builder.userId` for Authentication. [Smile ID — SmartSelfie enrollment compatibility](https://docs.usesmileid.com/developer-resources/sdks/web/web-sdk/performing-a-verification), [Smile ID — Enrolling and authenticating the same user](https://docs.usesmileid.com/developer-resources/sdks/mobile/performing-a-verification)
- In the v12 mobile SDK, `userId` and `jobId` are server-issued; Authentication is the exception where the app echoes the previously issued `userId`. The lower-level REST API also permits an optional partner-provided `user_id` for Biometric KYC/Enrollment, generated as a TypeID if omitted; Authentication requires an existing enrollee's `user_id`. [Smile ID — mobile invariants](https://docs.usesmileid.com/developer-resources/sdks/mobile), [Smile ID — Biometric KYC API](https://docs.usesmileid.com/api-reference/products/biometric-kyc/perform-a-biometric-kyc-verification), [Smile ID — Authentication API](https://docs.usesmileid.com/api-reference/products/smartselfie-authentication/authenticate-a-users-biometrics)
- `partnerConfig.partnerParams` is an optional string map sent as `partner_params` and echoed on the webhook; use it for non-PII correlation such as an internal attempt/session reference. [Smile ID — Setup, Partner params](https://docs.usesmileid.com/developer-resources/sdks/mobile/setup)
- REST acceptance is **202 Accepted**, returning `status`, `message`, `job_id`, `user_id`, and `created_at`; it is not the verification verdict. The SDK's `onResult` similarly returns a `JobSubmissionResponse` (`jobId`, `userId`, submission `status`, `message`, optional `createdAt`) or failure/cancelled/captured. [Smile ID — Authentication API](https://docs.usesmileid.com/api-reference/products/smartselfie-authentication/authenticate-a-users-biometrics), [Smile ID — Getting Result](https://docs.usesmileid.com/developer-resources/sdks/mobile/getting-result-of-a-verification)
- The final asynchronous verdict arrives at the backend webhook. Authentication and Biometric KYC use top-level `status` = `clear`, `attention`, `block`, or `error`, with `message`, machine-readable `reason`, timestamps, `partner_params`, and product-specific fields. Never log in/onboard from mobile `onResult` alone. [Smile ID — Getting Result](https://docs.usesmileid.com/developer-resources/sdks/mobile/getting-result-of-a-verification), [Smile ID — Authentication webhook](https://docs.usesmileid.com/developer-resources/essentials/verification-webhooks/webhook-types/smartselfie-authentication)

## Can login be vendor-liveness-only plus our own 1:1?

**Not through the documented Authentication contract.** `POST /v3/authentication` always describes passive liveness, active liveness, **and face matching** against the enrolled image; `user_id`, selfie, and liveness images are required. SmartSelfie Compare likewise performs vendor comparison against a supplied comparison image; it is not a liveness-only API. [Smile ID — Authentication API](https://docs.usesmileid.com/api-reference/products/smartselfie-authentication/authenticate-a-users-biometrics), [Smile ID — Compare API](https://docs.usesmileid.com/api-reference/products/smartselfie-compare/compare-a-selfie-to-an-image)

Our own embedding match can therefore be used in either of two architectures:

1. **Vendor-assured login:** run SmartSelfie Authentication and trust its final webhook; a private embedding is redundant for the basic decision, though it may be retained as an independent signal.
2. **Cost-minimized private login:** capture a fresh selfie and run our own liveness + 1:1 embedding match without submitting a Smile ID job. `skipApiSubmission` exposes the needed images, but its on-device capture feedback is only capture/face analysis, not a documented standalone liveness verdict; we must supply and validate the anti-spoofing control ourselves. [Smile ID — Getting Result](https://docs.usesmileid.com/developer-resources/sdks/mobile/getting-result-of-a-verification), [Smile ID — capture configuration](https://docs.usesmileid.com/developer-resources/sdks/mobile/performing-a-verification)

## Recovery, new devices, and offline behavior

- SmartSelfie Authentication is keyed to the enrolled `user_id`, not a documented device enrollment. A new device can therefore run a fresh Authentication job after our backend resolves the same stored `userId`; no separate new-device re-enrollment is specified. Device binding, step-up policy, and recovery authorization remain our responsibility. [Smile ID — Enrolling and authenticating the same user](https://docs.usesmileid.com/developer-resources/sdks/mobile/performing-a-verification)
- If no enrolled selfie exists, the asynchronous error is `image_unavailable_or_invalid` / “no enrolled selfie found for this user”; enroll first. Re-enrollment with `allow_new_enroll=true` replaces the existing enrollment, while the default `false` rejects an already-enrolled user. For high-risk account recovery, prefer a controlled step-up/re-KYC policy rather than silently replacing the biometric reference. [Smile ID — Errors](https://docs.usesmileid.com/api-reference/errors), [Smile ID — Enrollment API](https://docs.usesmileid.com/api-reference/products/smartselfie-enrollment/enroll-a-users-biometrics)
- Normal submission requires connectivity: the documented offline processing test produces `onResult.failure` with a network error, and no offline verification verdict is provided. `skipApiSubmission` leaves captured files available for our own retry queue, but secure storage, expiry, upload idempotency, and deletion are ours to implement. [Smile ID — Getting Result](https://docs.usesmileid.com/developer-resources/sdks/mobile/getting-result-of-a-verification)
- Offline Android **capture** has a separate model prerequisite: ML Kit's face model is normally downloaded by Google Play services. Devices that cannot download it cannot run selfie capture unless the app bundles `com.google.mlkit:face-detection:16.1.7`; this still does not make server verification offline. [Smile ID — Setup, offline devices](https://docs.usesmileid.com/developer-resources/sdks/mobile/setup)

Current pricing is therefore **sales-quoted/unclear from public official sources**. [Smile ID — Pricing](https://www.usesmileid.com/pricing), [Smile ID — Talk to an Expert](https://smile.id/talk-to-an-expert)
- The API does prove jobs draw on a prepaid balance: both Biometric KYC and Authentication document HTTP **402 — insufficient wallet balance**, and the error guide says to top up the Smile ID wallet. It does **not** publish the debit amount, retry billing rules, monthly minimum, or whether failed jobs are billed. [Smile ID — Authentication API](https://docs.usesmileid.com/api-reference/products/smartselfie-authentication/authenticate-a-users-biometrics), [Smile ID — Errors](https://docs.usesmileid.com/api-reference/errors)
- **No official source reviewed proved a hidden repeated per-call fee amount or minimum commitment, so none is asserted here.** Obtain a written quote covering Biometric KYC, each Authentication attempt, retries/failures, Enhanced Liveness, minimum spend, and wallet expiry before choosing vendor authentication for every login.

## Recommended cost-conscious flow

1. **Onboard once:** run Biometric KYC in the Expo dev/release build with `skipApiSubmission=true`; send the sealed job through our backend, retain exactly one enrollment selfie in private encrypted storage, compute/version our own embedding server-side, and delete device capture files after durable receipt.
2. **On the successful KYC webhook:** mark KYC approved, persist Smile ID's `userId` and our embedding/reference version. Do **not** purchase a separate SmartSelfie Enrollment job.
3. **Routine returning sessions:** prefer ordinary session/device credentials and reserve face checks for step-up events, avoiding a vendor job on every login.
4. **When face assurance is sufficient with our own controls:** run private liveness + 1:1 embedding matching with no Smile ID submission. Do not claim Smile ID liveness in this path.
5. **When vendor liveness/anti-spoofing is required** (for example new-device recovery or high-risk step-up): submit SmartSelfie Authentication using the stored `userId` and authorize only from the final `clear` webhook. Treat vendor face matching as included in that job, not as an optional component we can remove.
6. **Recovery fallback:** if the enrolled reference is absent/unusable or policy demands stronger proof, use controlled re-enrollment or fresh Biometric KYC; never silently overwrite a reference after a failed login. Queue offline captures only with strict encrypted expiry/deletion, and require connectivity before granting access.

The remaining decision is commercial and security-policy based, not SDK feasibility: compare the quoted cost of occasional vendor Authentication against the engineering and anti-spoofing burden of operating our own liveness for routine private matching.
