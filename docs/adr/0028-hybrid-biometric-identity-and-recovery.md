# Hybrid biometric identity: local 1:1, vendor KYC binding, and face-gated recovery

ADR-0022 originally alternated between self-held embeddings and vendor-held biometrics. This amendment replaces that either/or mode with a hybrid enrollment: one participant has an encrypted local embedding **and** a Smile ID `providerRef`. Smile ID performs Biometric KYC and identity binding; it does not return an embedding and is not on the repeat-login path.

## State and KYC

- `identity_participants.kyc_status` distinguishes staging `preverified` from real `verified`. Production proof issuance and enrollment require `verified`; the ADR-0004 production KYC gate is unchanged.
- `verifiedLegalName` is written once from a signed KYC result and is immutable. `displayName` remains editable. The completed enrollment job returns the vendor legal name as a suggestion for explicit display-name confirmation.
- Only the internal edge seam `POST /auth/enrollment-proof` can create/update an identity participant and issue a proof. Public enrollment cannot upsert a participant. The opaque proof is 256-bit random, SHA-256-hashed at rest, participant/purpose-bound, expires after 15 minutes, and is consumed by device-key registration.
- Device-key registration requires either a live same-participant session or that enrollment proof. Public device reset creation is gone; manual reset creation/decisions remain internal.

## Capture, hybrid enrollment, and login

Mobile captures seven fresh camera frames. Before capture or vendor submission it records explicit `biometric-capture-v2` consent, with a receipt persisted by the identity worker. Six to eight frames are required at every face capture boundary. Enrollment copy discloses retention of one current selfie; login and recovery copy discloses transit-only capture handling.

`POST /auth/face/enroll` validates the proof and calls only the private Node service's `/v1/face/embed` in hybrid mode. Smile ID Biometric KYC owns enrollment liveness and identity matching; local liveness is not a second mandatory enrollment gate. The Node service strips metadata/re-encodes the submitted device selfie, computes a finite 512-dimensional embedding from those normalized bytes, and returns the same bytes. Identity SHA-256-binds those bytes to the pending capture, the vendor submission, and the final enrollment. No provider callback/poll image can create or replace an embedding.

For hybrid enrollment, the identity worker encrypts the embedding into the pending job, stores the normalized selfie under an opaque `pending/` key in the identity-owned private R2 bucket, submits Biometric KYC, and returns 202. A signed `clear` result or poll promotes that exact object to `enrollments/`, finalizes `providerRef`, the local embedding, content hash, consent version/timestamp, and model version, then deletes any replaced selfie after the new enrollment commits. Pending artifacts clear on every terminal transition. Failed, mismatched, abandoned, and expired jobs delete the pending object; a five-minute scheduled sweep handles abandoned expiry. Migration `0015_identity_enrollment_capture_retention` is additive. R2 has no public URL, signed-URL, profile, or ops read path.

`POST /auth/face/verify` always invokes local fresh liveness, decrypts exactly the named participant's embedding, and performs in-memory 1:1 cosine matching without a vendor job. There is no email recovery, no 1:N identification, and no vector search. `POST /auth/recovery` currently applies the same participant identifier + fresh local liveness + 1:1 check, then revokes old device credentials and sessions before registering the replacement key and issuing a session. Five failed face attempts in 15 minutes trigger a 15-minute attempt window (429). Similarity remains banded in audit/wire responses. Smile ID SmartSelfie Authentication is reserved for a future new-device/high-risk step-up policy; that vendor route is a **TODO, not implemented or represented as recovery today**, and must never be added to every ordinary login.

## Private service and runtime honesty

`apps/biometrics` is a separate Dockerized Node service. Only `apps/identity` holds its bearer token; mobile and the marketplace edge cannot call it and there is no admin-key route. `FACE_MODEL_PATH` must name a real ONNX artifact. `/embed` loads only that face model and does not require `LIVENESS_MODEL_PATH`; routine local login/recovery still requires the real liveness artifact. Missing configured artifacts, missing production secrets, stub mode in production, non-finite/invalid model output, and failed liveness all fail closed.

The ArcFace and MiniFASNet preprocessing/inference structure was selectively adapted from `reference/bug-free-giggle` (`recognition/embedder.ts`, `liveness/antiSpoofing.ts`). No root LICENSE was present in the supplied reference repository. This is provenance, not a license grant; confirm redistribution permission before external distribution. Unrelated SDK, identification/1:N, API, and deepfake flows were not copied.

`FACE_MATCH_THRESHOLD` and `LIVENESS_THRESHOLD` are explicit runtime inputs. Existing 0.6 cosine and 0.8 liveness defaults are engineering placeholders, **not accuracy findings**. No accuracy, FAR/FRR, demographic-performance, or presentation-attack benchmark was run in this change; launch requires a versioned benchmark on the actual models, preprocessing, devices, and target population.

## Private capture handling contract

Raw JPEG frames exist in mobile memory, the TLS request to the existing edge `/auth/*` proxy, identity-worker request memory, and the TLS server-to-server request to the biometric service. The edge proxy must remain body-forwarding only: no capture logging, analytics, persistent request bodies, or media-library upload. Login/recovery frames are never written to Postgres, R2, logs, or responses. The single approved enrollment selfie is written only to the private identity R2 binding and is never returned by an API, profile, ops view, signed URL, or log. Provider submission follows the recorded consent and Smile ID's own retention terms. One current encrypted embedding and one current selfie replace their predecessors; there are no rolling templates. Pending embeddings and captures are deleted when the job terminates. Production deployments must set body-size limits and TLS at the proxy, use a private network for biometrics, and keep the R2 bucket private with platform encryption and least-privilege identity access.

**Remaining deletion requirement:** there is no participant account-deletion seam in this branch. Before account deletion is offered, its identity workflow must delete the current R2 selfie, any pending captures, the enrollment/embedding records, and issue supported vendor deletion requests, with backup/lifecycle handling documented. No deletion endpoint or completed vendor deletion is claimed here.

## Core integration

After ParticipantDO and the durable core profile are saved, the edge calls internal `POST /auth/enrollment-proof` with the same participant id, role, display name, and `verified` (or explicit-staging-only `preverified`) status, then includes the returned opaque `enrollmentProof` in `participant.recorded`. It does not log that proof. Pending or failed KYC receives no proof and no session. Existing participant ids and role-changing identity duplicates fail closed; a Bearer session cannot onboard another participant or role.

The onboarding command is document-only: email and explicit consent are required, and it carries neither biometric frames nor an R2 capture reference. Mobile sends fresh frames only through the direct `/auth/face/enroll` flow above. The existing `/auth/*` proxy remains generic, forwarding `PATCH` and `Authorization`, enforcing capture body limits, and honoring the no-capture-logging contract. `preverified` permits transactions only when `ALLOW_HEADER_AUTH=true`; production transactions and proof issuance require `verified`. Ordinary handoff evidence capture is unchanged.
