# Drizzle migrations — Postgres system of record (ADR-0011)

Postgres on **Neon**, reached from Workers via **Hyperdrive**. This is the
system of record — the double-entry ledger included; **money never lives in
D1**. See `schema.ts` for the full schema with doctrine notes.

## Layout

- `schema.ts` — Drizzle `pgTable` definitions. Glossary terms only; all money
  is `bigint` integer kobo; all timestamps are `timestamptz`; ids are `text`.
- `migrations/0000_init.sql` — bootstrap migration, **generated by
  `drizzle-kit generate`** from `schema.ts` (with `migrations/meta/_journal.json`
  so `drizzle-kit migrate` applies it). Never hand-edit SQL in `migrations/` —
  change `schema.ts` and regenerate.
- `drizzle.config.ts` — dialect `postgresql`, schema `./schema.ts`, out
  `./migrations`. The connection string is read from the environment
  (`DATABASE_URL`, falling back to `HYPERDRIVE`) and is **never hardcoded**.

## Running migrations

The connection string is a **secret**: the runtime binding is configured with
`wrangler secret put` (see `infra/wrangler.edge.toml` and `infra/README.md`),
and migrations run with the Neon connection string supplied via a CI secret or
a local env var — never committed.

```sh
# from this directory, with drizzle / drizzle-kit available in the workspace
DATABASE_URL="$NEON_CONNECTION_STRING" drizzle-kit migrate        # apply pending
DATABASE_URL="$NEON_CONNECTION_STRING" drizzle-kit generate       # diff schema.ts → new migration
```

`drizzle-kit migrate` connects to Neon directly (a developer machine or CI);
Hyperdrive is the runtime path from Workers, not the migration path.

## Open design decisions (founder sign-off)

- **Ledger chart of accounts** (`LEDGER_ACCOUNTS` in `schema.ts`):
  `buyer_capture`, `seller_payable`, `runner_payable`, `platform_revenue`,
  `buyer_refund`, `platform_loss`, with `party_id` distinguishing per-participant
  payables. Legs must balance (sum of debits == sum of credits) per
  `settlement_record_id`; the archive consumer writes them in one transaction.
- **No `participants` table** — Buyer/Seller/Runner ids are text references
  issued by the edge identity layer (ADR-0010 lists no participants table).
  Add an anchor table later if we need referential integrity or profiles.
- **Multiple settlements per run are allowed** (`settlement_records.run_id` is
  indexed, not unique) so an appeal under ADR-0007 can produce a replacement
  settlement; consumers take the latest.
